Development log

This is the phase-by-phase build history of boring-llm: what was implemented, how it was verified, and every real Boring compiler bug/gap found and fixed along the way. It used to live in the main README.md; moved here so the README can focus on presenting the project rather than its construction. See README.md for what the project is and how to run it.

Phase 0 done and verified against a real model file. src/gguf.br parses a GGUF file's header, all metadata value kinds (scalars, strings, arrays), and tensor-info list in pure Boring. Verified two ways against the real Qwen/Qwen2.5-0.5B-Instruct-GGUF q8_0 file (676MB, 291 tensors, 26 metadata keys, real production weights — not a toy fixture): cross-checked field-for-field against tools/inspect_gguf.py (the Python gguf package as ground truth) with an exact match, and independently verified by reading raw tensor bytes back out of a synthetic fixture (test/test_gguf.br) and confirming they match the source values bit-for-bit. Resolves this model's tied-vs-untied embedding question directly: it has a separate output.weight tensor (untied).

Note: boring run's interpreter OOMs on a file this size (a real, filed interpreter limitation — packed byte buffers are stored as one boxed Value per byte internally) — real-scale parsing goes through boring build + cargo build, same workaround whisper-boring already uses for its own large-array limitation. boring run is still used for fast dev-loop testing against the small synthetic fixture in test/fixtures/.

Phase 1 done and verified against the real model too. src/math.br (RMSNorm, NEOX-style RoPE, naive causal GQA attention, SwiGLU) + src/quant.br (Q8_0 dequantization) + src/model.br (config/weight loading, full forward pass) — pure Boring, no GPU. Verified against real llama-cpp-python logits (tools/reference_logits.py) for the prompt "The capital of France is" on both the fp16 and Q8_0 real GGUF files: every position's top-5 token ranking matches exactly, logit values agree to within float32-accumulation-order noise (a few hundredths on fp16, a bit more on Q8_0 near close ties — both expected, documented gaps, not bugs). Final-position top prediction is token 12095 ("Paris") on both files, matching llama.cpp exactly.

Phase 2b done and verified against the real Q8_0 model, on real Metal GPU hardware. Q8LinearKernel (src/math_gpu.br) dequantizes each weight element on the fly inside the tiled GEMM's shared-memory tile-load step, reading straight from GGUF's raw Q8_0-packed bytes — no full fp32 weight copy is ever materialized (for the LM head alone, 151936×896, that's the difference between ~146MB of packed bytes and a ~544MB dequantized copy). model.br's load_model_quantized/forward_gpu_quantized load every big matmul weight (Q/K/V/O projections, FFN gate/up/down, LM head) as raw bytes; only norms/biases (always F32 in real GGUF files) and the token-embedding lookup (dequantized one row at a time, not the whole table) touch the CPU. Verified: produces bit-identical output to Phase 2a's CPU-dequant-then-GPU-matmul path on the real model — same top-5 rankings, same logit values to the last printed digit.

Phase 4 (stretch): KV-cache incremental decode, done and verified. model.br's generate_kv()/forward_step()/prefill_gpu_quantized() replace "re-forward the whole sequence every step" with a real growing per-layer K/V cache: a single batched forward pass over the prompt (same kernels/dispatch count as the no-cache path, regardless of prompt length) seeds the cache, then each new token costs O(1) GEMM work per layer instead of O(current length) — only attention's own cost still scales with the cache size, which no KV-cache design avoids. Verified bit-identical output to the already-verified no-cache path on two different prompts (short and longer generations), and measurably faster once generation length is long enough to amortize per-call overhead (28 generated tokens: ~48s with --kv-cache vs. ~72s without, on the same prompt). For very short generations the no-cache path can still be marginally faster (fixed per-step dispatch overhead dominates before the O(seq)-vs-O(seq²) FLOP savings catch up) — both paths are kept, selectable via --kv-cache.

sh
./target/release/main --gguf ../../weights/qwen2.5-0.5b-instruct-q8_0.gguf --quantized \
    --prompt "What is the capital of France?" --max-tokens 30 --kv-cache

Phase 4 (stretch): temperature/top-k/top-p sampling, done and verified. src/sampling.br — a self-seeded xorshift64 PRNG (Boring has no builtin RNG; same precedent as scratch-boring's own Rng, kept purely functional here — rng_next_u64/rng_next_f32 return (value, new_Rng) rather than mutating in place) plus temperature scaling, a top-k pre-filter (bounded selection, no full 150k-entry sort), and top-p/nucleus filtering over the (already-sorted) top-k candidates. temperature <= 0 is still plain greedy argmax (the default, and what every earlier phase's verification used). Verified: --seed gives reproducible output for the same seed; different seeds diverge into genuinely different, coherent, on-topic completions at a higher temperature (three different short cat stories from three seeds); a highly-confident completion ("The capital of France is Paris.") stays the same across seeds/greedy, as expected when one continuation dominates the probability mass regardless of sampling settings.

sh
./target/release/main --gguf ../../weights/qwen2.5-0.5b-instruct-q8_0.gguf --quantized --kv-cache \
    --prompt "Tell me a short story about a cat." --max-tokens 40 \
    --temperature 1.3 --top-k 60 --top-p 0.95 --seed 3

Phase 4 (stretch): k-quant formats beyond Q8_0, done and verified. src/quant.br adds dequantize_q5_0/dequantize_q6_k/dequantize_q4_k — a legacy 5-bit format and two real "superblock" k-quant formats (256-element blocks with quantized per-sub-block scales, Q4_K's own quantized per-sub-block minimums too), ported bit-for-bit from ggml's own dequantize_row_q5_0/q6_K/q4_K. Qwen2.5-0.5B-Instruct-Q4_K_M.gguf (the model this name usually refers to) turns out to be a genuine mix of five tensor formats depending on layer/role (F32 norms/biases, Q5_0 for token embeddings and FFN gate/up, Q8_0 for some attention/output tensors, Q6_K and Q4_K split across different ffn_down layers) — all three new dequantizers, plus the already-existing F32/F16/Q8_0 ones, now load correctly and produce real end-to-end generation. Verified two ways: the exact real superblock bytes from this file, dequantized in Boring and cross-checked element-for-element against Python's gguf package's own dequantize() (test/test_quant_kquant.br); and full text generation ("What is the capital of France?" → "The capital of France is Paris.", matching every earlier phase's verified output) on the real, fully-mixed-format file.

sh
./target/release/main --gguf ../../weights/qwen2.5-0.5b-instruct-q4_k_m.gguf \
    --prompt "Tell me a short story about a cat." --max-tokens 40 --temperature 1.0 --top-k 40 --top-p 0.9 --seed 5

Scope note: these three new formats go through the same "dequantize once at load, run ordinary fp32 GPU kernels" path Phase 2a already proved (generate_f32/forward_gpu) — none of them got their own fused-dequant-inside-the-GEMM-kernel treatment the way Q8_0 did in Phase 2b (--quantized stays Q8_0-only, and has no KV-cache-free variant for these formats yet). A real follow-up, not attempted here, given how much more involved Q4_K/Q6_K's bit-unpacking already is just on the CPU side — and every lesson from Phase 2b's Q8LinearKernel (inline everything into the kernel's own def() body; no kernel-method or free-function-with-array-parameter factoring works on Metal) would still apply, just with considerably more logic to inline per element.

Phase 4 (stretch): warp-shuffle GEMM reduction — implemented, verified correct, honestly not a performance win. math_gpu.br's LinearWarpKernel/linear_warp_gpu uses gpu.warp.* (real, working primitives — warp.lane/warp.size/shuffle_xor, verified first on an isolated micro-kernel, then on this real GEMM shape) for a one-warp-per-output-cell reduction with zero shared memory and zero block-wide barriers, the exact follow-up boring's own warp-level-primitives.md names for this project's tiled kernels. Verified numerically correct against linear_gpu (small hand-picked values and a d_in=100 case exercising multiple warp-stride rounds). Benchmarked honestly (test/bench_linear_warp.br, real Metal hardware, this model's actual dimensions) — and it's slower, not faster: ~1.5x slower at attention/FFN-projection scale (d_in=896, d_out=896), ~2.4x slower at LM-head scale (d_in=896, d_out=8192). Removing the barrier was never the bottleneck here — linear_gpu's shared-memory tile is a real data-reuse mechanism (every input loaded from global memory once, reused by a whole 16x16 block of threads); this kernel has none of that, so far more redundant global-memory bandwidth is spent than the barriers it removes were ever costing. Same lesson as the KV-cache work: measure wall-clock at this project's real sizes, don't assume "fewer synchronization points" means "faster." Kept in the codebase (correct, independently verified, real production dispatch/grid-overflow handling) alongside linear_gpu, not swapped in anywhere — a properly warp-aligned tiled+shuffle hybrid (keep the shared-memory reuse, use shuffles only for the final in-warp reduction step) is the real follow-up this result points to, not attempted here.

cd test/bench_linear_warp_metal && cargo build --release
./target/release/bench_linear_warp tiled-big   # linear_gpu

Phase 4 (stretch): wgpu backend verification — done completely, and it drove 12 real boring compiler fixes. Rebuilt test/test_math_gpu_real.br under --target wgpu (the only alternative GPU backend with real testable hardware on this machine, via Metal-backed wgpu — CUDA/ROCm still have no available hardware) and worked through failures one at a time, same source verified correct on --target metal throughout. Found and filed 12 distinct, real boring wgpu-backend bugs/gaps along the way, in three broad clusters:

  • Codegen correctness: a literal-division-by-zero Inf/NaN construction rejected by WGSL's compile-time-constant rules; .powf()/.ln()/.signum()/.cbrt()/.log10() transpiling to nonexistent WGSL identifiers instead of pow/log/sign/etc.; a non-literal block-size dispatch dimension silently becoming workgroup size 1 (fixed twice — once for top-level let constants, once more for constants local to the enclosing function); a workgroup-shared field-name collision between two different kernel structs; a stray & breaking host-function-to-host-function chaining.
  • Kernel init()-setup dropped in host wrapper functions: a cluster of related-looking cases (an init()-derived scalar field staying 0, a .reshape()'d input's axis-dimension fields never assigned) that shared one systemic root cause in the wgpu host-codegen path.
  • Missing capability: [uint8]-element storage buffers weren't supported at all (WGSL has no 8-bit storage type) — first landed as a correct compile-time rejection instead of silent data corruption, then as full support via transparent array<u32> packing; and the wgpu device-creation code requested wgpu::Limits::default() (a conservative 128 MiB max buffer-binding size) instead of the adapter's real capability (confirmed ~9.5 GB really available on this machine), which blocked any buffer bigger than that — including this model's ~144 MB LM-head weight.

All 12 are now fixed upstream in boring itself and reverified with zero regression. Every source-level workaround added while chasing them — the flat-array/manual-indexing rewrites in TransposeKernel/MatMulBTHeadsKernel/SoftmaxRowsKernel/MatMulHeadsKernel, RopeApplyKernel's recomputed half_dim and log2/exp-based .powf() replacement, the q8_tile_x/q8_tile_w field rename, io.br's runtime-derived-zero Inf/NaN construction, linear_warp_gpu's literal-8 block-size dispatch — was reverted back to clean, idiomatic Boring source. Also cleaned up in the process, once the host-function-chaining bug was confirmed fixed: model.br's passthrough() round-trip, previously mandatory at every GPU-host-function-to-GPU-host-function boundary throughout forward_gpu/forward_gpu_quantized/prefill_gpu_quantized/forward_step (~150 call sites), is now only needed where a value is actually iterated (for..in) or placed into a struct constructor/tuple directly.

Final result: the full compiled kernel suite (test_math_gpu_real.br, every kernel, no exceptions) passes on --target wgpu with zero source-level workarounds, and the real CLI's end-to-end Q8_0 chat generation — GGUF parsing, tokenizer, the full 24-layer forward pass, sampling, all chained together against the actual downloaded model weights — produces bit-identical output to --target metal ("The capital of France is Paris.", with and without --kv-cache). Both backends are now equally real, equally verified. CUDA/ROCm remain untested (no hardware available on this machine for either).

Remaining Phase 4 ideas, not started: CUDA/ROCm verification (no hardware available to test either).

Generalizing model.br beyond Qwen2 — done for weight/config loading, verified against a real Llama-architecture GGUF. config_from_gguf already read every hyperparameter from GGUF's own per-architecture {arch}.* metadata keys rather than hardcoding Qwen2's own values, so the remaining gaps were: Qwen2's attention Q/K/V bias tensors ({prefix}.attn_{q,k,v}.bias), which Llama/Mistral GGUFs simply don't write at all — load_tensor_f32_or_zero now falls back to an all-zero bias vector when the tensor is absent, a no-op once added onto linear_bias's output; and RoPE's rotation convention, which turned out to genuinely differ by architecture and isn't stored anywhere in GGUF metadata itself.

Downloaded a real TinyLlama-1.1B-Chat-v1.0 GGUF (architecture = "llama", GQA 32 query / 4 KV heads, no bias tensors) and ran it through the existing --tokens debug path (bypassing the tokenizer, same Phase-1 methodology used for Qwen2) against llama-cpp-python's own logits on the same hand-picked token IDs. Every position matched exactly at pos 0 (no RoPE rotation happens there — cos(0)=1) but diverged increasingly from pos 1 onward — a strong signal the bug was specifically in how multi-position rotation was applied, not in weight loading or attention itself (confirmed further by getting byte-identical wrong output from both the CPU-only and GPU-fused-kernel paths, ruling out a kernel-specific bug).

Rather than trust a hazy memory of which architecture uses which RoPE convention, fetched llama.cpp's actual llama_model_rope_type() switch table (src/llama-model.cpp) directly: LLM_ARCH_LLAMA (which also covers plain Mistral — it has no separate architecture string in llama.cpp, only newer Mistral3/Mistral4 do) resolves to LLAMA_ROPE_TYPE_NORM, the original "interleaved" GPT-J-style rotation (adjacent pairs (2j, 2j+1)) — not the NEOX "rotate-half" style (pairs (j, j+half_dim)) this project's rope_apply/RopeApplyKernel had hardcoded from Qwen2's own (correct, LLAMA_ROPE_TYPE_NEOX) requirement. Confirmed empirically before committing to the fix: swapping the index formula from (j, j+half_dim) to (2j, 2j+1) in a scratch edit turned the growing divergence into a near-exact top-5 logit match (differences of ~0.01-0.05 in absolute logit value, the same float32-accumulation-order noise already accepted for Qwen2's own Q8_0 verification) — then reverted that blanket edit and threaded a real Config.rope_neox flag (from a new rope_style_for_arch, throwing on any architecture string not in {"qwen2", "llama"} rather than silently guessing) through math.br's rope_apply/rope_apply_at and math_gpu.br's RopeApplyKernel/rope_apply_gpu/rope_apply_at_gpu instead, so Qwen2's own NEOX path stays exactly as it was.

Re-verified with zero regression: the full test_math_gpu_real.br/test_quant_kernels_real.br suites, and real end-to-end generation on Qwen2.5 (Q8_0, Q4_K_M, fp16, with and without --kv-cache) all still produce the exact same output as before ("The capital of France is Paris."). On the new TinyLlama file, the --tokens debug path now matches llama-cpp-python almost exactly at every position (only a single 4th-ranked near-tie token differs at one position, well inside the noise band already accepted elsewhere in this project). Phase 5 (post-MVP shared-library extraction with whisper-boring) — considered, decided against. Diffed this project's math_gpu.br/io.br against whisper-boring's once both were stable: the genuinely identical surface turned out to be small (TransposeKernel, SoftmaxRowsKernel, and io.br's LE binary readers — a few hundred lines) — LinearKernel (pre-transpose contract vs. GGUF's native layout) and the head-mapping kernels (GQA vs. no GQA) have real, load-bearing differences that aren't safely unifiable without genuine design work, not just a mechanical extraction. Decision: not worth a new shared repo's overhead for that little truly-common code — keep both projects' kernels independent. (Also surfaced, in passing, unrelated to this decision: whisper-boring's io.br still has the naive per-byte UTF-8 decoder this project's own bytes_to_str used to have — currently harmless there since it's only ever applied to ASCII tensor names, but worth knowing if that ever changes.)

SentencePiece tokenizer for the Llama/Mistral family — implemented and verified against real TinyLlama weights, first try on every test prompt. tokenizer.br's encode/decode now dispatch on GGUF's own tokenizer.ggml.model key ("llama" → SentencePiece, anything else → the existing GPT-2/Qwen2 byte-level BPE), rather than assuming Qwen2's tokenizer family unconditionally. encode_spm is a from-scratch reimplementation of llama.cpp's own llm_tokenizer_spm_session::tokenize (src/llama-vocab.cpp, read directly rather than guessed): split the space-prepended, whitespace-escaped-to-"▁" text into one symbol per Unicode character, then repeatedly merge the currently-adjacent pair whose concatenation is itself a valid vocab entry with the highest tokenizer.ggml.scores value (ties toward the leftmost pair), falling back to the vocab's own <0xXX> byte tokens for anything that never merges into a known piece. Implemented as a plain O(n²) rescan-per-merge instead of llama.cpp's priority queue — deliberately simpler to get right in Boring, and fine at this project's actual scale (short interactive prompts, not long-context batch tokenization). Also skips llama.cpp's rev_merge/resegment fallback entirely: since a merge only ever happens when the merged span is already a confirmed vocab entry, any symbol that underwent at least one merge is guaranteed to look itself up successfully afterward — only a genuinely never-merged single character can miss and need the byte-fallback path, so there's no case rev_merge was ever needed to recover from.

New gguf_get_f32_array (gguf.br) reads tokenizer.ggml.scores, mirroring the existing gguf_get_int_array/gguf_get_string_array. Verified against a real downloaded TinyLlama-1.1B-Chat GGUF (test/test_tokenizer_spm_real.br) across five prompts chosen to stress different parts of the algorithm — a plain sentence, punctuation and digits, consecutive spaces (SentencePiece vocabs carry dedicated multi-space tokens like "▁▁", not just repeated single-space merges), and accented non-ASCII text (exercises the byte-fallback path) — token-for-token identical to llama-cpp-python's own .tokenize()/.detokenize() on every one, first attempt. Zero regression confirmed on the existing Qwen2 BPE path (test_tokenizer_real.br, full local interpreter suite, and a real end-to-end Qwen2 Q8_0 KV-cache chat generation, all unchanged).

Deliberately not attempted: wiring this into --prompt/--chat for a Llama-family GGUF — main.br only ever calls encode_chat/encode_chat_multi/encode_chat_turn (Qwen2.5's own hardcoded ChatML wrapping, which looks up <|im_start|>/<|im_end|> in the vocab and throws cleanly when they're absent, as already confirmed for TinyLlama), never a raw tok.encode() call. The tokenizer-format gap is now closed; the chat-template gap (a real Jinja tokenizer.chat_template evaluator, needed since Llama/Mistral models each have their own, GGUF-embedded template) is the next, separately-tracked piece needed before real generation works end-to-end on this family.

A real Jinja2-subset interpreter (src/jinja.br) — implemented and verified byte-for-byte against real jinja2, on both Qwen2.5's own tool-calling-capable template and TinyLlama's simpler one, first correct render after fixing 2 real boring bugs and one design gap of its own. User explicitly asked for the wider subset (not just enough for TinyLlama) after seeing Qwen2.5's real tokenizer.chat_template — a genuine ~2.5KB template with tool-calling, {% set %}, is defined, and | tojson, not just simple {% if %}/{% for %}. Two-level grammar (a template-level lexer/parser splitting Text/{{ }}/{% %} into an AST of SText/SOutput/SIf/SFor/SSet nodes, each {{ }}/{% %}'s inner source parsed as its own recursive-descent expression AST — JExpr — at load time), fully handling Jinja's {%-/-%}/{{-/-}} whitespace-trim markers (every real template found in the wild leans on them). JValue is a small tagged-union enum (JStr/JInt/JBool/JList/JDict/JUndefined) standing in for Jinja's dynamically-typed values.

Env threading (set, for-loop variables, loop.first/last/index/index0) is done entirely via return values ((String, {string=JValue})), the same "new state, old state kept around" idiom as the KV-cache/RNG work elsewhere in this project — required, not just stylistic preference here: a same-scope var copy = original; ...; original = copy pattern (copy a dict, mutate the copy, write the result back into the variable the copy came from) hits a real, newly-confirmed boring checker bug (a var dict wrongly reported "immutable" on the write-back, even though it's declared var — filed as task_c44f5882). Isolated via a from-scratch minimal repro (no loop needed) before filing, confirming the taint is specifically about writing back into a same-scope copy-source, not about dict mutation or loop-reassignment in general (both of which work fine when routed through an actual function call/return, which is exactly the pattern this file already needed).

Two more real, distinct boring bugs found and fixed with confirmed workarounds while building this:

  • task_13987ec4: a {K=V} dict bound by an enum match pattern (match v: JDict(fields): fields[key]) has its indexing mis-transpiled as ARRAY indexing under --target metal (fields.get(key as usize), a hard compile error casting the string key to usize) — confirmed the taint survives copying to a fresh let first, and confirmed dicts reached via an ordinary struct field or a plain function parameter are unaffected (only the match-binding itself is tainted). Workaround (used throughout jinja.br's jv_get_attr/jv_get_index): route the match-bound dict through a small dedicated function that returns it as a plain value, then index that function's return value directly.
  • task_0d22152f: (struct_field as int) — casting a string-typed struct field directly — mis-transpiles under --target metal as a numeric isize::try_from(...) conversion instead of the correct string-parse codegen, even though a bare local or plain parameter of the same type casts correctly. Workaround: copy the field into a plain local first (let s = t.text; guard let n = (s as int) else throw ...).

One bug of its own (not boring's) found and fixed: the template-level lexer's tag-closing scan needs to track string-literal quote state (with backslash-escape skipping) while looking for }}/%} — Qwen2.5's own template has a {{ "...{"name": ...}..." }} output block (a JSON-literal string nested inside a Jinja expression), and without quote-tracking a } occurring inside that nested string could in principle be misread as part of the closing delimiter. Fixed in scan_raw's inner scanning loop.

One genuine Jinja semantic (not a bug at all, easy to miss): real Jinja2's keep_trailing_newline=False default — used by every real chat-template consumer, including transformers' apply_chat_template — unconditionally drops exactly one trailing newline from the raw template source before parsing, independent of any - trim marker on the template's last tag. Real GGUF chat_template strings always end with a plain text-editor newline after their final {% endif %}; without replicating this, rendering Qwen2.5's real template produced one extra trailing "\n" that real jinja2 doesn't. Fixed with a small strip_one_trailing_newline pass in parse_template, caught immediately by the "left/right" assertion diff in test/test_jinja_real.br rather than a subtle silent mismatch.

Verified two ways: a new interpreter-speed test/test_jinja.br (no real GGUF needed — small hand-written templates covering every construct: output, if/else, for-loops with loop.*, attribute/index access, string concat, boolean logic, is defined, set, tojson, the trailing-newline quirk) and test/test_jinja_real.br (a real --target metal build against both real downloaded GGUFs, rendering the SAME real tokenizer.chat_template string gguf_get_string reads at runtime, for a single-turn and a 4-message multi-turn conversation each, comparing byte-for-byte against real jinja2's own output — including TinyLlama's untrimmed template, whose messy, blank-line-heavy default whitespace behavior is actually a better stress test of the no-trim-marker code path than Qwen2.5's heavily-{%- -%}-optimized one). All pass, first correct render after the fixes above — no remaining known discrepancies against either real template.

Deliberately not attempted (scope boundary, explicit): wiring render_jinja into main.br's --prompt/--chat path. Doing so needs one more real piece first — teaching the tokenizer to recognize special-token text (<|im_start|>, <s>, <|user|>, ...) embedded in a Jinja-rendered prompt STRING and encode it as its own atomic vocab id, instead of running the whole rendered string through ordinary BPE/SentencePiece merging (which would tokenize the literal characters <, |, i, m, ... instead of recognizing the special token) — llama.cpp's own tokenizer_st_partition, deliberately not ported here yet. 2026-10-08 — Incremental SSE streaming

Until now a stream: true reply was generated in full and then written as one SSE body: right framing, no streaming. The decode loop moved from model.br (generate_kv_resume, replaced by prefill_resume) into handle_chat, so each token can be written as it is sampled. Design points:

  • Incremental decode. After each token the server decodes a small window of the reply's tokens twice (up to the previous read offset and up to now) and takes the difference, advancing the window only when the new text does not end in U+FFFD — a byte-level token boundary can fall inside a UTF-8 character, so a half character is never sent.
  • What is safe to send (stream_bounds, openai.br, pure and unit-tested): the same range parse_reply would call content (trimmed, nothing from <tool_call> on), minus a tail that could still grow into <tool_call> or a stop string. The range only ever extends, so what was already sent is always a prefix of what follows; the unit test feeds replies one character at a time and asserts that for each prefix. At the end the server sends whatever of the authoritative content (one full decode + parse_reply) was not sent yet, then the tool calls (one delta), the finish chunk, usage and [DONE].
  • Stop strings now end generation as soon as one appears (the old path generated all max_tokens and cut afterwards); the stop token is not fed back, so the cache covers cache.pos tokens as for EOS.
  • Error handling. A module static var response_state tells serve whether anything was written: before any byte a failure is a JSON 500; with a stream open it ends with an SSE error event + [DONE]; a client that left mid-stream just aborts the request ("socket write failed") and the server keeps going.

A latent bug surfaced on the way: bytes_to_str (io.br) read past the end of the buffer on a truncated multi-byte sequence and panicked the whole server — reachable before this work too (a reply cut by max_tokens inside a character) but certain with window decoding. It now yields U+FFFD for truncated or invalid sequences (one per byte of the bad prefix), covered by test_tokenizer.br.

Verified (Metal and wgpu): the 7 baseline checks and the 11-request server sequence byte-identical (the non-streaming path was refactored), smoke_server.py extended with incremental checks (many content events, first content before 60% of the total time, no Content-Length, streamed text and finish reason equal to the buffered ones, stop string cuts and shortens generation, streamed tool call equal to the buffered one, tool syntax never in content) all passing; streamed UTF-8 replies (accents, emoji, CJK, Cyrillic, Greek) equal the buffered ones with no U+FFFD; a client disconnecting mid-stream leaves the server serving; a 450-token reply costs 28.4 ms/token streamed vs 28.6 buffered.

Not done: OpenCode itself has still not been run against the server (its provider package needs a download that needs the user's OK); the tool call is sent as a single delta rather than name-then-arguments increments (valid for OpenAI clients, which accumulate by index).

2026-10-08 (night) — The prompt cache survives a restart

--prompt-cache DIR (src/prompt_cache.br, wired into server.br/main.br): after a request, serve writes the KV cache the request left (first tokens.length positions of every layer, float32 as the GPU holds it) to DIR/prompt-cache-<n>.bin when it covers at least 1024 tokens and adds at least 1024 to what the disk has; the write happens after the socket is closed (serve_conn owns the connection). A request whose prompt shares at least 256 more tokens with a snapshot than with any in-memory slot restores those positions (read per layer, uploaded with upload_floats_gpu) instead of prefilling them; if the restore fails the request falls back to a plain prefill. The file is 32-byte header | token ids | per layer K rows then V rows; the header (magic, version, model fingerprint, shape, token count, sequence number) is written last and the size is checked against the shape, so a half-written or truncated file is ignored, and so is a snapshot made by another model (fingerprint = file size, n_layer, kv_dim, a hash of the first and last 64 KB of tensor data). --prompt-cache-files N (default 2) bounds the disk use: the snapshot being extended is replaced, else a free file, else the oldest.

Reading a 'gpu'unified struct field back to the host needs a kernel round trip (download_floats_gpu; passthrough only takes host arrays), and upload_floats_gpu got the same 2-D grid as upload_bytes_gpu (a 16k-token context of a 7B model is 8.4M floats per buffer).

Method: tools/metal_prefill_lab/ (stand-alone MSL + a Swift timing harness, GPU clock, median of 5 runs of 4 back-to-back dispatches; M3 10-core, load average 3-5 so differences under ~3% are noise). base.metal transcribes boring's Q4_K prefill schedule (64x32 tile, 8 simdgroups, k step 32, float32 staging) and reproduces the kernel: m = 512, n = 18,944, k = 3,584 gives 1.58 TFLOP/s (1.47 measured through boring; the copy has no bias or edge code) and its result is within 1.3e-6 (relative) of a CPU dequantization on 48 sampled outputs. stage removedmsshare
matrix multiply + store only (nothing else)21.750% (3.2 TFLOP/s: the ceiling of simdgroup_multiply_accumulate on this GPU, float32 or half alike)

So the multiply is half of the time and the rest is stages that do not overlap with it: a threadgroup fills its tiles, hits a barrier, multiplies, hits a barrier. Half staging removes ~2.5 ms of tile stores (1.71 TFLOP/s) but not the structure.

What changed in tiled.metal (fragment-blocked threadgroup tiles: every 8x8 fragment contiguous, loaded with stride 8; the weight tile stored n-major and loaded with the transpose flag, so a thread dequantizes 8 consecutive k of one column and writes one 16-byte vector; one scale decode per 8-16 weights; 64x64 or 128x64 output tile): float32 staging 2.07 TFLOP/s (+31%, bit-identical output to the current schedule), half staging up to 2.45 (128x64 tile, 4x2 simdgroups, k step 64: +43% over the current half schedule, same 3e-4 half rounding as before). What did not matter: tile traversal order (weights are not bandwidth bound), register prefetch of the next step's global loads (slightly worse), k step 64 with float staging (worse: 32 KB of tile leaves one group per core). Refuted: invisible per-launch copies or allocations. 2026-10-10 — Batch only the decode section

boring now exposes a native set_gpu_batch_limit(int) runtime hook. Metal stores the threshold in a thread-local mutable cell and commits the current partial command buffer before changing policy; CUDA and wgpu provide compatible no-ops. forward_step selects eight launches per command buffer and restores one before returning, so the launch-heavy single-token path gets the measured batching benefit without imposing it on GPU-bound prefill.

On Qwen2.5-0.5B Q8_0, adjacent runs of the same 200-token raw-id decode took 5.07 seconds with a threshold of one and 4.49 seconds with eight, both including the same model load. Generated ids were byte-for-byte identical. This removes launch submission as the easiest remaining gap; the next short-context target is a genuinely fused Q/K/V projection rather than further tuning of the already launch-bound 128-row matvec.
