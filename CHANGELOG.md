# Changelog

All notable user-visible changes to boring-llm. The format follows [Keep a Changelog](https://keepachangelog.com/); the project has not made a release yet, so everything is under *Unreleased*.

## [Unreleased]

### Added

- **Jinja: a much larger subset** (`src/jinja.br`): operators `~ * / // % **`, floats, chained comparisons, `and`/`or` returning an operand, list/tuple/dict literals, slices with a step, string indexing; about 40 filters with arguments (`join`, `default`, `map`, `selectattr`, `sort`, `tojson(indent=n)`, `indent`, `format`, ...), more tests (`odd`, `divisibleby`, `eq`, `in`, ...), dict/string methods (`items`, `get`, `split(sep, maxsplit)`, `rsplit`, `find`, ...), `dict()` and `strftime_now`; `for ... else`, loop filters, tuple unpacking, `loop.revindex/length/previtem/nextitem/cycle`, multi-target and block `set`, `macro` (defaults, keyword arguments), `{# #}` comments and `{% raw %}`. New `tools/jinja_diff.py` renders 175 small templates with `jinja2` and with `src/jinja.br` (driver `test/jinja_driver.br`): 65 agreed before, 167 now. Still unsupported (reported as errors): `include`/`import`/`extends`, `call` blocks, `with`, `filter` blocks, `break`/`continue`, `batch`, `cycler`, mutating methods such as `list.append`; `{{ none }}` prints nothing (a JSON null is read as undefined). TinyMixtral's real template renders identically to `jinja2` on all five request fixtures with the new interpreter, and `tools/oracle_render_request.py` now defines `raise_exception`.
- **f16 and q8_0 KV caches for Gemma 2/3**: their extended attention (head size 256, soft-capping, sliding windows) reads a widened float32 copy of the packed main cache at each decode step. That path already joined the whole cache every step, so the per-token cost is about the same while storage stays packed; prefill widens and repacks as it does for other models. Gemma 2 2B Q4_K_M decodes 120 tokens with `-ctk f16` and `-ctk q8_0` with exactly the same results as float32 (one prompt identical to llama.cpp for all 120 tokens, two differing only at near-ties with gaps 0.10 and 0.00). Gemma 3 270M Q8_0 gives identical results in f32, f16 and q8_0 as well (two prompts identical to llama.cpp for all 120 tokens, one differing at token 19 with a 0.57 gap in every mode). The attention is not fused for head size 256, so this saves memory, not time.
- **f16 and q8_0 KV caches for any head size that is a multiple of 32 up to 128** (they were limited to 64 and 128): Phi-3 mini (96) now works. The attention tests cover 32, 64, 96 and 128 on real Metal, and Phi-3.1 mini Q4_K_M decodes 120 tokens with `-ctk f16` and `-ctk q8_0` identically to each other, within llama.cpp near-ties (gaps 0.00-0.05, one divergence past a tail fold at token 69). Gemma 2/3 (head size 256, extended attention path) still need their own kernels.
- **Phi-3 and Gemma 2 checked on real weights** (Q4_K_M, against llama.cpp's CPU backend, `tools/accuracy_vs_llamacpp.py` and `tools/decode_vs_llamacpp.py`): Phi-3.1 mini 4k 584/613 top-1 (95.3%, mean logit difference 0.165, one reference token outside our top 5), Gemma 2 2B 586/613 (95.6%, 0.123, none outside). Decoding agrees on all 32 tokens for one prompt of each model and differs only at near-ties (gaps 0.00-0.10) on the others. The prompts are far shorter than Gemma 2's 4096-token sliding window, so the window itself is still only covered by the synthetic fixtures. `tools/fetch_models.py` knows both files.
- **Q8_0 KV cache** (`-ctk q8_0 -ctv q8_0`): the main K/V planes are stored as int8 values plus one float16 scale per block of 32 (`src/q8kv_gpu.br`: scales, quantize, append, dequantize and a decode attention kernel that widens at the point of use; the float32 tail and the general prefill attention are unchanged, as for f16). Works through prefill, chunked prefill, batched passes, folds, cache truncation and disk snapshots (still float32 on disk). Head sizes 64/128 only, K and V the same type, no Gemma 2/3. `test/test_q8kv_gpu_real.br` checks round trip, append and attention on real Metal; `tools/decode_vs_llamacpp.py --binary-args '-ctk q8_0 -ctv q8_0'` on Qwen2.5-0.5B Q8_0 agrees with llama.cpp on 97 of 97 tokens for one prompt (past a tail fold) and differs on two prompts only at near-ties (logit gaps 0.19 and 0.01), as f32/f16 do for the latter.
- **Granite (dense) and SmolLM3**: Granite's four scales (embedding, attention, residual, logit) and SmolLM3's rotary-free every-fourth layer, on the CPU reference and every quantized GPU path. Tiny synthetic models agree with a numpy reference that llama.cpp reproduces to 0.0004 (Granite) and 0.003 (SmolLM3), and the Metal Q8_0 versions match it in prefill and decode. Real files, Q4_K_M, against llama.cpp's Metal backend: Granite 3.3 2B 604/613 top-1 (mean logit difference 0.050), SmolLM3 3B 611/613 (0.033); against its CPU backend 586/613 and 582/613 (0.124 and 0.162), which differ from its own Metal backend by the same amount (CPU activation quantization), so the CPU-based accuracy tool reports SmolLM3 just under its 95% threshold. Decoding agrees on 3 prompts for both (32 tokens, one 0.00-gap near-tie on each).
- **Mixture of experts** (Mixtral layout: `llama` with `expert_count`; `qwen3moe`): router softmax, top-k, renormalized weights (llama.cpp's `build_moe_ffn`), experts as separate resident buffers, rows gathered per expert, on the CPU reference and every quantized GPU path (full forward, chunked prefill, KV-cache decode). Verified three ways: tiny synthetic MoE models (`tools/make_arch_test_ggufs.py`) agree with a numpy reference that real llama.cpp reproduces to 0.004; the same models on Metal (Q8_0) match the reference to 1e-5 in prefill and decode (also with chunked prefill); and a real Mixtral-layout GGUF, TinyMixtral-4x248M (4 experts, 2 used), against llama.cpp's Metal backend gives 613/613 top-1 (mean logit difference 0.0014) in Q8_0 and 612/613 (0.007) in Q4_K_M (against its CPU backend 601/613 and 573/613, the usual CPU-activation noise). Not run on Qwen3-30B-A3B (it does not fit in this machine's GPU memory). Each layer costs one host round trip for routing; shared experts and DeepSeek-style routing are not supported.
- **Speculative decoding by prompt lookup** (`--spec-type ngram-simple`, `--draft-max`, `--draft-min`, `--spec-ngram-size-n`): the n-gram that ends the text so far is looked up in the prompt and the reply, the tokens that followed it are fed with the sampled token in one batched pass (`forward_batch_gpu_quantized`, logits of every row), and each sampler choice that equals the next drafted token reuses its row instead of a decode step; the first mismatch truncates the KV cache (`resume_cache`) and decoding goes on normally. Every token still comes from the real sampler on the real logits, so streaming, stop strings, grammars, logprobs and cache reuse work unchanged and greedy replies were identical to plain decoding in all runs. A pass that gains fewer than two tokens pauses drafting for 2-16 steps. Measured with a repeated passage: 1.67x on Qwen2.5-0.5B and 1.49x on TinyLlama 1.1B; on free text 0.7-0.9x on the 0.5B model and 1.1x on TinyLlama, hence off by default. The batched pass reads all rows' logits back to the host, which is the first thing to remove.
- **GBNF grammars**: the `grammar` request field (and `--grammar` / `--grammar-file` as server defaults) constrains decoding with llama.cpp's grammar format, implemented as its stack machine (`src/grammar.br`: parser with repetition, classes, groups, escapes and comments, incremental matcher; `test/test_grammar.br`, including llama.cpp's own `json.gbnf`). With the same grammar, greedy replies on Qwen2.5-0.5B Q8_0 equal llama.cpp's for a yes/no choice, a JSON array and the full JSON grammar; a digit grammar differed only by a 0.05-logit near-tie between two digits. Lazy grammars and trigger words are not supported.
- **IQ4_XS** (CPU dequantization identical to the Python `gguf` package, tiled / single-row / dequantize-then-matmul kernels like the other hand-written formats) and IQ4_NL moved to the lane-per-block kernels (the compiler's tensor schedule is no longer used for it). The real Qwen2.5-0.5B IQ4_XS file (IQ4_XS, IQ4_NL, Q5_1 and Q8_0 tensors, bartowski's quantization) gives 596/613 top-1 and mean logit difference 0.057 against llama.cpp, generation in agreement; per-format synthetic models match the numpy reference to 1e-5. The other IQ formats (IQ1-IQ3, which need large lookup grids) and MXFP4 are still missing.
- **Embeddings** (`--embeddings`, `--pooling none|mean|cls|last`): `/v1/embeddings` (OpenAI, float or base64) and llama-server's `/embedding` / `/embeddings` serve the pooled final-norm hidden state of a decoder model, with `embd_normalize` (default euclidean). Against llama.cpp on Qwen2.5-0.5B Q8_0 (not an embedding model; it checks the mechanics): cosine similarity 0.9995-0.9997 for mean and last pooling, 0.993-0.999 for cls. Rerank pooling and bidirectional (BERT-style) architectures are not supported.
- **The synthetic-model references are checked against real llama.cpp** (`tools/arch_vs_llamacpp.py`): the tiny `test/fixtures/arch-*.gguf` carry a minimal vocabulary, so llama-cpp-python loads them, and its logits agree with the float64 numpy transcription that `test/test_arch.br` and the Metal checks use to within 0.005 on every F32 fixture (plain, YaRN, linear scaling, Phi-3 factors, Gemma 1/2/3 with soft-capping, sliding windows and `rope.freq_base_swa`). It also settled two open points: llama.cpp ignores `attention.sliding_window` for the `llama` architecture (so Mistral needs nothing), and it picks Phi-3's long RoPE factors when `n_ctx` (padded to 256) exceeds `original_context_length`; boring-llm now does the same from `--ctx-size`.
- **More tensor formats**: Q4_1, Q5_1, Q5_K, F16 and BF16 as matrix weights and embeddings (CPU dequantization identical to the Python `gguf` package on random blocks, `test/test_quant_formats.br`; tiled prefill kernels and single-row warp kernels). Checked on a tiny model per format against the numpy reference (`tools/make_arch_test_ggufs.py --formats`; prefill and decode on Metal) and on the real Qwen2.5-0.5B Q5_K_M file (Q5_1, Q5_K, Q6_K and Q8_0 tensors): 599/613 top-1 and mean logit difference 0.063 against llama.cpp, generation in agreement. These formats have no native tensor schedule. Decode kernels give each lane whole blocks (the first version, where a warp decoded one block jointly with a lane-0 broadcast, was ~4-6x slower); prompts of 16 rows or more dequantize once and use the float32 tiled matmul (a 613-token forward of the Q5_K_M model: 15 s -> ~5 s). That model now decodes ~2x slower than the Q8_0 one (was ~10x; timings taken on a loaded machine, ratios from repeated runs). Q4_0 and Q5_0 use the same kernels (6x faster than the compiler's tensor schedule on a resident matvec benchmark; real Qwen2.5-0.5B Q4_0 file: 604/613 and 0.065 against llama.cpp). F32 matrices are not supported on the GPU path; IQ1-IQ3, IQ4_XS and MXFP4 are still missing.
- **Several end-of-generation tokens**, as in llama.cpp: the tokenizer registers the EOS, the GGUF's `eot`/`eom` ids and the well-known end-of-turn tokens present in the vocabulary (`<end_of_turn>`, `<|im_end|>`, `<|eot_id|>`, `<|endoftext|>`, ...), and every generation loop (CLI, chat, server, constrained JSON/tool sampling) stops on any of them; `ignore_eos` suppresses all of them, and a reply cut by the length limit is closed with the template's own turn-end token. Gemma replies now end at `<end_of_turn>` (`finish_reason: "stop"`) instead of repeating it. Qwen2.5 also stops on `<|endoftext|>` now.
- **RoPE scaling and more architectures**: linear, YaRN, Llama 3.1 (`rope_freqs.weight`) and Phi-3 per-pair RoPE factors (one frequency table replaces `freq_base` in the CPU, wgpu/Metal kernels and the fused decode kernel); Phi-3 (`phi3`: fused `attn_qkv` / `ffn_up` split at load) and Gemma 1 (`gemma`: GeGLU, embeddings scaled by sqrt(d_model), head size independent of d_model / n_head). Verified on tiny synthetic models (`tools/make_arch_test_ggufs.py`, `test/test_arch.br`) against an independent float64 numpy transcription of llama.cpp's graph: logits agree to ~3e-6 on the CPU path and to 3 decimals on the Metal quantized prefill and decode paths. **Not run on real Phi-3/Gemma/YaRN weights**, and the real-model accuracy checks against llama.cpp were not re-run after the RoPE table change (no weights were available). Phi-3's long factors are selected from `--ctx-size` (see below); Mistral's `attention.sliding_window` is ignored, as llama.cpp does for the `llama` architecture.
- **Gemma 2 and 3** (`gemma2`, `gemma3`): post-attention/post-FFN norms, attention-score and final-logit soft-capping, sliding-window layers, per-layer RoPE tables, explicit attention scale. Checked on tiny synthetic models against the numpy reference (CPU, and Metal prefill and decode); Qwen2.5-0.5B and TinyLlama 1.1B Q8_0 still pass the llama.cpp accuracy and decode checks unchanged. Run on the real Gemma 3 270M Q8_0: against llama.cpp's Metal backend 613/613 top-1 and mean logit difference 0.011 (against its CPU backend 576/613 and 0.297, but llama.cpp's CPU and Metal backends differ from each other by exactly that much: the CPU one quantizes activations to Q8_0), and generation agrees (32 tokens on two prompts, a 0.57 near-tie on the third). That file has no `rope.freq_base_swa` key, so the default 10000 applies; a file that carries the key has not been seen.
- **Jinja subset**: slices (`messages[1:]`, `xs[:-1]`), `a if cond else b`, and integer `%` / `*`, as Gemma 3's chat template needs; its real template renders identically to jinja2 (with and without a system message).
- **Qwen3 support** (`qwen3` architecture; Qwen3-4B Q4_K_M tested): the head size is read from `attention.key_length` (128 for the 4B, not `d_model / n_head`), the per-head RMS norm of queries and keys is applied before RoPE, and the NEOX rotation is selected for the name. Against llama.cpp on the CPU, position by position (`tools/accuracy_vs_llamacpp.py`, 313 positions): 302 top-1 agreements and mean logit error 0.134, the same on Metal and wgpu; Qwen2.5 results are unchanged.
- **Reasoning output**: `<think>...</think>` text is returned as `message.reasoning_content` (and as `reasoning_content` deltas when streaming), the answer as `content`; the markers never reach either. `chat_template_kwargs` in a request reaches the chat template (`enable_thinking: false` for a direct answer). An assistant message with `content: null` is read as an empty string.
- **A larger Jinja subset** for Qwen3's chat template: `namespace(...)` with `{% set ns.attr = ... %}`, `range(...)`, the string methods `split`, `strip`, `lstrip`, `rstrip`, `startswith`, `endswith`, `replace`, `lower`, `in`/`not in`, comparisons, negative indices, the tests `is string/none/false/true/mapping/number/sequence`, the `length` filter, `raise_exception`, correct `not` precedence and per-loop scoping of `set`. Rendered prompts of Qwen2.5 and Qwen3 are identical token for token to `jinja2`'s on every request fixture (multi-turn tool calls, reasoning history, `enable_thinking`).
- **`tools/fetch_models.py`**: downloads the models the tests and tools use into `weights/` on demand (nothing is downloaded unless asked), with resume and SHA-256 verification against Hugging Face; `tools/accuracy_vs_llamacpp.py` and `tools/bench_vs_llamacpp.py` take `--model NAME [--fetch]`. `tools/oracle_render_request.py` compares a build on all request fixtures.
- **A more useful context-overflow error**: the 400 `context_length_exceeded` now says how many tokens the prompt has and what the context is, tells the user to shorten the conversation or raise `--ctx-size`, carries `n_prompt_tokens` and `n_ctx`, and contains the phrases clients and llama.cpp use for the same condition ("maximum context length", "exceeds the available context size").
- **More request fields** on `/v1/chat/completions`: `top_k`, `repeat_penalty`, `frequency_penalty`, `presence_penalty`, and `tool_choice: "none"` (tools left out of the prompt, no tool call returned). Other `tool_choice` values are accepted but not enforced.
- **Continuous integration** also runs the stdlib self-tests of the llama.cpp comparison tools and checks that the generated HTML documentation is up to date; the interpreter test loop skips every `*_real.br` by pattern.
- `test/test_quant_kernels_real.br` now also runs tensor schedules with 70 rows (prefill) and a bias on real tensors, covering the Q6_K odd-column case that single-row checks miss.
- **Documentation book** (`docs/book.md`, 15 chapters: command line, HTTP API, agents, formats, caches, performance, architecture, GPU backends, verification, development guide, troubleshooting) and `docs/build.py`, which generates `docs/book.html`, the other `docs/*.html` and `README.html` with no dependency beyond Python 3.
- `tools/accuracy_vs_llamacpp.py`: model-level accuracy check against llama.cpp on the CPU (same token ids, top-1 agreement and mean logit difference at every position of a 313-613 token text, exit status for CI-style use). It caught three compiler regressions that the kernel tests missed; run it for every `boring` update that touches the GPU kernels, on a Q8_0 and a Q4_K_M model.
- `tools/metal_prefill_lab/`: stand-alone Metal kernels and a timing harness for the quantized prefill matmul (per-stage cost of the native schedule, alternative tile layouts), used to specify the faster schedule now in `boring`.
- `tools/bench_vs_llamacpp.py`: speed comparison with llama.cpp (llama-cpp-python) on the same GGUF file, alternating engines, streamed requests timed on the client side (prefill and decode tokens/s, min/median/max), refusing to run on a busy machine.
- **Disk prompt cache** (`--prompt-cache DIR`, `--prompt-cache-files N`, `--prompt-cache-max-mb N`): the KV cache a request leaves is written to disk and reused by later requests, also after a restart. Snapshots are tied to the model that wrote them, ignored when incomplete, and bounded in number and total size. A 6.4k-token prompt takes ~13 s cold and 0.5-1.5 s restored on the 0.5B model; OpenCode's first 7.6k-token request on the 7B model goes from 321 s of prefill to 1.9 s after a restart.
- **Streaming starts before the prompt is processed**: the SSE head and role chunk are sent at once and a comment line follows every 512 prompt tokens, so clients that drop a silent response after 5 minutes (OpenCode) survive a cold 7B prompt. A client that disconnects mid-prefill stops the prefill.
- **Qwen2.5-7B-Instruct Q4_K_M runs** (token embedding over 268 MB no longer breaks the loader).
- **Native Metal Q4_K and Q6_K kernels** for prefill and decode, enabled in `boring.toml` (3B Q4_K_M: prefill 177 to ~16-26 ms/token, decode 4.2 s to ~0.11-0.22 s/token). `--kquant-prefill handwritten` keeps the hand-written prefill kernels on wgpu/CUDA/ROCm, where they are still faster.
- **Disk-streaming GGUF loader**: only the header is parsed from memory, tensors are read when needed (3B server: 13.6 GB peak to 3.3 GB, ready in 5 s instead of 60 s).
- **OpenCode works end to end**: tool calls survive the garbled closing braces small models produce, and `tools/opencode_trial.sh` runs a real OpenCode against a server in an isolated configuration.
- **Incremental SSE streaming** of chat completions (role, content deltas, tool calls, finish reason, usage, `[DONE]`), `stop` strings that end generation, and several in-memory prompt-prefix caches (`--cache-slots`).
- **OpenAI-compatible server** (`--serve`): `/v1/models`, `/v1/chat/completions` with tool calling through the model's own chat template.
- **Chat templates**: a Jinja2 subset interpreter renders the GGUF's own template (Qwen2.5, TinyLlama), checked byte for byte against `jinja2`.
- **KV-cache reuse across chat turns** in `--chat --kv-cache`.
- Quantization formats Q4_0, Q5_0, Q8_0, Q2_K, Q3_K, Q4_K, Q6_K, IQ4_NL (with F32/F16), checked against real weights on Metal and wgpu; SentencePiece tokenizer for Llama-family models.
- **`tools/decode_vs_llamacpp.py` and `--generate-tokens`**: a decode-path check against llama.cpp. The binary generates greedily from raw token ids through the KV-cache path (prefill, then one `forward_step` per token) and prints the ids; the tool compares them with llama.cpp's continuation of the same ids and, at the first difference, requires llama.cpp's own logit gap between its token and ours to be below 1.0 (a near-tie). The logits check (`--tokens`) never runs `forward_step`, so it cannot see a decode-only bug. Healthy: all of Qwen2.5-0.5B Q8_0/Q4_K_M, 3B and 7B pass with gaps of 0.01 to 0.33; the removed fusion below fails with gaps of 3 to 6.

### Changed

- **Metal launch batching is now enabled automatically only during KV-cache decode.** `forward_step` selects batches of eight launches through `boring`'s runtime hook and restores the default before returning, so prefill keeps one launch per command buffer. An adjacent 200-token Qwen2.5-0.5B Q8_0 run fell from 5.07 to 4.49 seconds wall clock (including identical model loading), with byte-for-byte identical generated ids. The independent decode oracle remains unchanged: two 32-token continuations agree completely and the third is the same accepted 0.01-logit near-tie.
- **RMSNorm now uses one GPU SIMD group per row** instead of one thread serializing the whole hidden dimension. On Qwen2.5-0.5B Q8_0 this raises decode from 43.15 to 61.35 tok/s at ~570 tokens and from 29.48 to 41.45 at ~4,150 tokens (three-run medians), while prefill rises from 1,704 to 1,813 and from 1,076 to 1,112 tok/s. Accuracy remains 594/613 top-1 with 0.062 mean logit difference against llama.cpp. A later run of the same code measured 52.2 and 44.0 tok/s through the server (machine state moves absolute numbers by tens of percent); the CLI ratio, 21.2 to 14.7 ms per token, is +44%.
- **Metal inference is substantially faster.** Native quantized prefill, cooperative Q8_0 decode, improved Q4_K decode, launch batching and the two-buffer KV cache reduce prompt and token latency while preserving the llama.cpp accuracy and decode checks. Current reproducible measurements are documented in the README performance table.
- Prefill is chunked (512 tokens) with a fused flash-style attention for `d_head` 64 and 128, decode uses a split-K attention kernel, and the KV cache and residual stream stay on the GPU: a 5.6k-token prompt went from ~43 s to ~11-15 s and decode at that context from 127 to ~20 ms/token (0.5B Q8_0).
- BPE encoding costs O(word) instead of O(merges).
- `tools/opencode_trial.sh` is a single braced block, so editing it while a trial runs cannot change what the running copy executes.

### Fixed

- **JSON Schema responses were only checked once the value closed.** The old `json_schema` / `response_format` decoder only kept the text a valid JSON prefix, so with an object schema a model could start a string or a number and run into the token limit with a reply that matches nothing (`"20230101000000000...` for `{"type":"object","required":["n"]}`). A schema is now compiled to a GBNF grammar (`src/schema_grammar.br`) and decoded under it: type, enum, const, anyOf/oneOf, local `$ref` (also recursive), object properties/required/additionalProperties, array items/minItems/maxItems, string length. On Qwen2.5-0.5B Q8_0 the replies are valid and equal llama.cpp's grammar-constrained ones for three schemas. Numeric ranges, `pattern` and `format` are not enforced while decoding. `json_object` and tool calls keep their previous decoders.
- **The fused Q/K/V decode result now stays GPU-resident after tuple destructuring.** Its three destructured slots are explicitly `'kernel'unified`; without those annotations the generated Metal host code downloaded Q and K after every layer before uploading them again for Q/K normalization or RoPE. The corrected `forward_step` contains no intermediate device-to-host copy, and the llama.cpp decode oracle remains unchanged (two complete 32-token agreements and the same accepted 0.01-logit near-tie on the third prompt).
- **Residual updates no longer target a copied GPU buffer.** The unsafe residual-add/RMSNorm fusion was removed; decode verification now covers this state-passing path against llama.cpp.
- Truncated or invalid UTF-8 in a streamed or `max_tokens`-cut reply no longer panics.

### Known issues

- Q4_1, Q5_1, Q5_K, Q4_0 and Q5_0 decode ~3-6x slower than Q8_0 on a resident matvec (`test/bench_decode_formats.br`): the byte-wise loads, not the activation loads, dominate; a four-columns-per-warp variant gained only ~15% and was dropped.
- wgpu/CUDA/ROCm prefill of K-quants through the portable tensor schedule is ~3x slower than the hand-written kernels.
- CUDA and ROCm have never been run.
- Requests are served one at a time.
