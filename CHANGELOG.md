# Changelog

All notable changes to boring-llm. The format follows [Keep a Changelog](https://keepachangelog.com/); the project has not made a release yet, so everything is under *Unreleased*. `docs/development-log.md` is the longer story (measurements, dead ends, bugs found in `boring`); this file lists what a user of the engine can see.

## [Unreleased]

### Added

- **Qwen3 support** (`qwen3` architecture; Qwen3-4B Q4_K_M tested): the head size is read from `attention.key_length` (128 for the 4B, not `d_model / n_head`), the per-head RMS norm of queries and keys is applied before RoPE, and the NEOX rotation is selected for the name. Against llama.cpp on the CPU, position by position (`tools/accuracy_vs_llamacpp.py`, 313 positions): 302 top-1 agreements and mean logit error 0.134, the same on Metal and wgpu; Qwen2.5 results are unchanged.
- **Reasoning output**: `<think>...</think>` text is returned as `message.reasoning_content` (and as `reasoning_content` deltas when streaming), the answer as `content`; the markers never reach either. `chat_template_kwargs` in a request reaches the chat template (`enable_thinking: false` for a direct answer). An assistant message with `content: null` is read as an empty string.
- **A larger Jinja subset** for Qwen3's chat template: `namespace(...)` with `{% set ns.attr = ... %}`, `range(...)`, the string methods `split`, `strip`, `lstrip`, `rstrip`, `startswith`, `endswith`, `replace`, `lower`, `in`/`not in`, comparisons, negative indices, the tests `is string/none/false/true/mapping/number/sequence`, the `length` filter, `raise_exception`, correct `not` precedence and per-loop scoping of `set`. Rendered prompts of Qwen2.5 and Qwen3 are identical token for token to `jinja2`'s on every request fixture (multi-turn tool calls, reasoning history, `enable_thinking`).
- **`tools/fetch_models.py`**: downloads the models the tests and tools use into `weights/` on demand (nothing is downloaded unless asked), with resume and SHA-256 verification against Hugging Face; `tools/accuracy_vs_llamacpp.py` and `tools/bench_vs_llamacpp.py` take `--model NAME [--fetch]`. `tools/oracle_render_request.py` compares a build on all request fixtures.
- **A more useful context-overflow error**: the 400 `context_length_exceeded` now says how many tokens the prompt has and what the context is, tells the user to shorten the conversation or raise `--ctx-size`, carries `n_prompt_tokens` and `n_ctx`, and contains the phrases clients and llama.cpp use for the same condition ("maximum context length", "exceeds the available context size").
- **More request fields** on `/v1/chat/completions`: `top_k`, `repeat_penalty`, `frequency_penalty`, `presence_penalty`, and `tool_choice: "none"` (tools left out of the prompt, no tool call returned). Other `tool_choice` values are accepted but not enforced.
- **Continuous integration** also runs the stdlib self-tests of the llama.cpp comparison tools and checks that the generated HTML documentation is up to date; the interpreter test loop skips every `*_real.br` by pattern.
- `test/test_quant_kernels_real.br` now also runs the tensor schedules with 70 rows (prefill) and a bias on real tensors, which catches the Q6_K odd-column bug that the single-row checks missed (fails on `boring` 8bdac11d, passes on d38813c8).
- **Documentation book** (`docs/book.md`, 15 chapters: command line, HTTP API, agents, formats, caches, performance, architecture, GPU backends, verification, development guide, troubleshooting) and `docs/build.py`, which generates `docs/book.html`, the other `docs/*.html` and `README.html` with no dependency beyond Python 3.
- `tools/accuracy_vs_llamacpp.py`: model-level accuracy check against llama.cpp on the CPU (same token ids, top-1 agreement and mean logit difference at every position of a 313-613 token text, exit status for CI-style use). It caught three compiler regressions that the kernel tests missed; run it for every `boring` update that touches the GPU kernels, on a Q8_0 and a Q4_K_M model.
- `tools/metal_prefill_lab/`: stand-alone Metal kernels and a timing harness for the quantized prefill matmul (per-stage cost of the native schedule, alternative tile layouts), used to specify the faster schedule now in `boring`.
- `tools/bench_vs_llamacpp.py`: speed comparison with llama.cpp (llama-cpp-python) on the same GGUF file, alternating engines, streamed requests timed on the client side (prefill and decode tokens/s, min/median/max), refusing to run on a busy machine.
- **Disk prompt cache** (`--prompt-cache DIR`, `--prompt-cache-files N`, `--prompt-cache-max-mb N`): the KV cache a request leaves is written to disk and reused by later requests, also after a restart. Snapshots are tied to the model that wrote them, ignored when incomplete, and bounded in number and total size. A 6.4k-token prompt takes ~13 s cold and 0.5-1.5 s restored on the 0.5B model; OpenCode's first 7.6k-token request on the 7B model goes from 321 s of prefill to 1.9 s after a restart.
- **Streaming starts before the prompt is processed**: the SSE head and role chunk are sent at once and a comment line follows every 512 prompt tokens, so clients that drop a silent response after 5 minutes (OpenCode) survive a cold 7B prompt. A client that disconnects mid-prefill stops the prefill.
- **Qwen2.5-7B-Instruct Q4_K_M runs** (token embedding over 268 MB no longer breaks the loader).
- **Native Metal Q4_K and Q6_K kernels** for prefill and decode, enabled in `boring.toml` (3B Q4_K_M: prefill 177 to ~16-26 ms/token, decode 4.2 s to ~0.11-0.22 s/token). `--kquant-prefill handwritten` keeps the hand-written prefill kernels on wgpu/CUDA/ROCm, where they are still faster.
- **Disk-streaming GGUF loader**: only the header is parsed from memory, tensors are read when needed (3B server: 13.6 GB peak to 3.3 GB, ready in 5 s instead of 60 s).
- **OpenCode works end to end**: tool calls survive the garbled closing braces small models produce, and `tools/opencode_trial.sh` runs a real OpenCode against a server in an isolated configuration.
- **Incremental SSE streaming** of chat completions (role, content deltas, tool calls, finish reason, usage, `[DONE]`), `stop` strings that end generation, and several in-memory prompt-prefix caches (`--cache-slots`).
- **OpenAI-compatible server** (`--serve`): `/v1/models`, `/v1/chat/completions` with tool calling through the model's own chat template.
- **Chat templates**: a Jinja2 subset interpreter renders the GGUF's own template (Qwen2.5, TinyLlama), checked byte for byte against `jinja2`.
- **KV-cache reuse across chat turns** in `--chat --kv-cache`.
- Quantization formats Q4_0, Q5_0, Q8_0, Q2_K, Q3_K, Q4_K, Q6_K, IQ4_NL (with F32/F16), checked against real weights on Metal and wgpu; SentencePiece tokenizer for Llama-family models.
- **`tools/decode_vs_llamacpp.py` and `--generate-tokens`**: a decode-path check against llama.cpp. The binary generates greedily from raw token ids through the KV-cache path (prefill, then one `forward_step` per token) and prints the ids; the tool compares them with llama.cpp's continuation of the same ids and, at the first difference, requires llama.cpp's own logit gap between its token and ours to be below 1.0 (a near-tie). The logits check (`--tokens`) never runs `forward_step`, so it cannot see a decode-only bug. Healthy: all of Qwen2.5-0.5B Q8_0/Q4_K_M, 3B and 7B pass with gaps of 0.01 to 0.33; the removed fusion below fails with gaps of 3 to 6.

### Changed

- **Metal launch batching is now enabled automatically only during KV-cache decode.** `forward_step` selects batches of eight launches through `boring`'s runtime hook and restores the default before returning, so prefill keeps one launch per command buffer. An adjacent 200-token Qwen2.5-0.5B Q8_0 run fell from 5.07 to 4.49 seconds wall clock (including identical model loading), with byte-for-byte identical generated ids. The independent decode oracle remains unchanged: two 32-token continuations agree completely and the third is the same accepted 0.01-logit near-tie.
- **`boring` a08df631 is the new recommended minimum for Metal Q8_0 decode.** Its large-projection specialization fully unrolls the four private row accumulators: resident Qwen2.5-0.5B shapes improve from 98.1 to 75.5 us for gate/up (47.2 to 61.3 GB/s), 93.1 to 70.1 us for down (49.7 to 66.0 GB/s), and 2,420 to 2,029 us for the tied head (59.8 to 71.3 GB/s). The isolated projection totals predict about 1.8 ms/token saved; end-to-end runs were too variable for a stronger claim. The decode-path oracle passes 32 generated tokens on all three prompts (one accepted 0.01-logit near-tie).
- **RMSNorm now uses one GPU SIMD group per row** instead of one thread serializing the whole hidden dimension. On Qwen2.5-0.5B Q8_0 this raises decode from 43.15 to 61.35 tok/s at ~570 tokens and from 29.48 to 41.45 at ~4,150 tokens (three-run medians), while prefill rises from 1,704 to 1,813 and from 1,076 to 1,112 tok/s. Accuracy remains 594/613 top-1 with 0.062 mean logit difference against llama.cpp. A later run of the same code measured 52.2 and 44.0 tok/s through the server (machine state moves absolute numbers by tens of percent); the CLI ratio, 21.2 to 14.7 ms per token, is +44%.
- **`boring` 1faf71e2 is the new recommended minimum for Metal.** Its four-row Q8_0 decode schedule raises Qwen2.5-0.5B Q8_0 from 23.08 to 43.15 tok/s at a ~570-token context and from 16.77 to 29.48 at ~4,150 tokens (three-run medians); model accuracy stays exactly at 594/613 top-1 and 0.062 mean logit difference against llama.cpp.
- **`boring` 46c2473f was the previous minimum**: it includes the fragment-blocked Metal quantized prefill (d38813c8, with the Q6_K odd-column fix) and the `.split()` transpilation fix this project needs. Measured against llama.cpp on an otherwise idle M3 (medians, prompts of ~570 and ~4,150 tokens): prefill 0.91x and 0.71x on Qwen2.5-7B (it was 0.53x), 0.66x and 0.59x on Qwen3-4B, 0.71x and 0.58x on the 3B, 0.62x and 0.56x on the 0.5B; decode 0.59x and 0.61x on the 7B, 0.20x to 0.58x on the others (the 0.5B is overhead-bound). OpenCode's cold first request on the 7B: 115 s of prefill (it was 130 s, 321 s before the disk cache). Accuracy against llama.cpp is unchanged: 0.5B Q8_0 594/613 and 0.062, 0.5B Q4_K_M 601/613 and 0.061, 7B 298/313 and 0.157, Qwen3-4B 302/313 and 0.134.
- **Prompt processing is ~3.5x faster on Metal and decode ~2.5x faster** with `boring` aada545d: native Metal quantized prefill 0.5 -> 1.4-1.5 TFLOP/s with float32 staging (half precision is an opt-in `precision = "half"`), Q4_K single-token decode 15 -> 19-64 GB/s. Qwen2.5-7B Q4_K_M: prefill ~26 -> ~70-100 tok/s, decode ~2.9 -> ~7-8 tok/s; against llama.cpp 0.14-0.20x -> 0.53x on prefill and 0.24-0.29x -> 0.58-0.63x on decode. OpenCode's first request (7.5k tokens) on the 7B model: 321-453 s of prefill -> 130 s. Accuracy is unchanged: against llama.cpp on the CPU, position by position, 0.5B Q8_0 613/613 top-1 and mean logit error 0.061, 0.5B Q4_K_M 612/613 and 0.070, 7B Q4_K_M 312/313 and 0.248, the same as with the old kernels.
- **Decode is ~2.5x faster on the 7B model**: the native Metal Q4_K decode kernel of `boring` (b090f49c; ~15 GB/s for every shape before, 19-64 GB/s now) and a KV cache split in a main buffer and a 64-row tail (`GenCache.tail`): appending a token no longer copies the whole cache per layer, only the tail, which is folded into the main buffers every 64 tokens. Qwen2.5-7B Q4_K_M, 570-token context: 2.9 to ~7.3 tok/s; 7.6k-token context (OpenCode): 2.5 to ~6.3 tok/s (the tail alone is worth ~21% there, within noise at 2k tokens). Outputs are unchanged (checked against the previous binary on the 0.5B models, across tail folds, on a 5-request sequence with every prefix-reuse case, on Metal and wgpu, and through the disk cache).
- Prefill is chunked (512 tokens) with a fused flash-style attention for `d_head` 64 and 128, decode uses a split-K attention kernel, and the KV cache and residual stream stay on the GPU: a 5.6k-token prompt went from ~43 s to ~11-15 s and decode at that context from 127 to ~20 ms/token (0.5B Q8_0).
- BPE encoding costs O(word) instead of O(merges).
- `tools/opencode_trial.sh` is a single braced block, so editing it while a trial runs cannot change what the running copy executes.

### Fixed

- **Generation printed random text after commit 1efb7c9 ("Fuse residual add with RMSNorm"), now fixed by removing that fusion.** The fused kernel declared its residual input `mut`, and a `mut` kernel field built from a resident argument is a copy (the generated wrapper calls `__boring_metal_buffer_copy`), so the attention output was added to a copy and every layer lost it. The kernel unit test only checked the normalized output, the model oracle uses a path the commit did not touch (`forward_gpu_quantized`), and the benchmarks count tokens, not their text; the 62.6 and 53.2 tok/s published for it were measured on a model that generated garbage. The fusion gave no speed anyway (14.7 ms/token with and without it on the 0.5B). The compiler gap that stops a correct version (two outputs through a tuple-returning `req`) is `boring` task `task_bfb8b121`.
- Truncated or invalid UTF-8 in a streamed or `max_tokens`-cut reply no longer panics.

### Known issues

- wgpu/CUDA/ROCm prefill of K-quants through the portable tensor schedule is ~3x slower than the hand-written kernels.
- CUDA and ROCm have never been run.
- Requests are served one at a time.
